# Брокерский заголовок в ордерах BingX / Bitget / MEXC через Pipedream

Дата: 12.10.2026. Источники: код github.com/PipedreamHQ/pipedream (ветка master), документация pipedream.com/docs.

## Коротко

- Готовые компоненты Pipedream брокерский заголовок **не ставят**, и параметра для своих заголовков в них нет.
- Решение есть: **свои приватные действия (custom tools) в Connect**. Они работают от подключённого аккаунта пользователя, а подключение остаётся в один клик через Pipedream. Нужен Business-план Pipedream.
- API-прокси Connect для этих бирж не подходит.

## 1. Как устроены готовые компоненты

**BingX** — `components/bingx/bingx.app.mjs`

- Ключи берутся из `this.$auth.api_key` и `this.$auth.secret_key` (стр. 174–179).
- Подпись: HMAC-SHA256 по query-строке, передаётся в параметре `signature` (стр. 185–190, `getParams`).
- Заголовки (стр. 147–153): `"X-BX-APIKEY": ..., ...headers`. Свои заголовки подмешиваются, а `makeRequest({ path, version, params, headers, ...args })` (стр. 155–170) их принимает. Значит, технически `X-SOURCE-KEY` можно передать через `headers`.
- Но **ни одно действие этот аргумент не передаёт**. `trade-new-order` вызывает `createOrder({ params, $ })`.
- Действие **«BingX Generic API Call»** (`actions/generic-api-call`) принимает только `httpMethod`, `apiPath`, `apiVersion` и `params`. Поля для заголовков в нём нет.

**Bitget** — `components/bitget/bitget.app.mjs`

- Ключи берутся из `$auth`: `api_key`, `secret_key`, `secret_passphrase`, `demo_environment` (стр. 363–369).
- Подпись: base64(HMAC-SHA256) от строки `timestamp+METHOD+/api/v2+path+body`, функции `preHash` и `sign` (стр. 334–361).
- `getHeaders()` (стр. 381–391) возвращает фиксированный набор: `ACCESS-KEY`, `ACCESS-PASSPHRASE`, `ACCESS-TIMESTAMP`, `ACCESS-SIGN`, `paptrading`, `locale`, `Content-Type`.
- В `makeRequest` (стр. 395–405) сначала разворачивается `...args`, затем идёт `headers: this.getHeaders(...)`. Поэтому **любые переданные заголовки перезаписываются**, и стандартным путём `X-CHANNEL-API-CODE` не добавить.
- Generic-действия у Bitget нет.

**MEXC** — `components/mexc/mexc.app.mjs`

- Это пустая заготовка: `propDefinitions: {}`, единственный метод `authKeys()` печатает ключи `$auth`.
- Действий нет совсем. В папке только `mexc.app.mjs` и `package.json`.
- Через Pipedream у MEXC есть только сама авторизация: пользователь вводит ключ и секрет. Подписание и ордера придётся писать самим.

## 2. Pipedream Connect: свои действия и прокси

**Свои действия (custom tools).** Это поддерживается официально: https://pipedream.com/docs/connect/components/custom-tools

- Пишется обычное действие на Components API и публикуется командой `pd publish my-action.mjs --connect-environment production`.
- После публикации оно доступно во всех Connect API (list, retrieve, run) с префиксом `~/`, например `POST /v1/components/~/ascn-bingx-place-order/run`.
- Оно также автоматически появляется как инструмент в Pipedream MCP для этого приложения.
- Ограничения:
  - **только Business-план**;
  - только действия, без триггеров;
  - среды development и production разделены.
- Запуск идёт так же, как у публичных действий (https://pipedream.com/docs/connect/components/actions): в `configured_props` передаётся проп приложения с `authProvisionId` подключённого аккаунта (`apn_...`). Внутри действия доступны `this.bingx.$auth.api_key` и `this.bingx.$auth.secret_key`, то есть ключи конечного пользователя.

**Отдельного режима «запустить произвольный код» в Connect нет.** Механизм для своего кода — это опубликованные custom tools.

**API Proxy** — https://pipedream.com/docs/connect/api-proxy

- Прокси сам подставляет учётные данные в заголовок или параметр URL. Пробрасываются заголовки с префиксом `x-pd-proxy-`.
- Поддерживает ли прокси конкретное приложение, показывает флаг `connect.proxy_enabled` в `/apps`.
- Для BingX, Bitget и MEXC стоит «Not available». В документации причина не названа. Скорее всего, дело в том, что эти API требуют подписывать каждый запрос HMAC от секрета, тела и времени, а прокси умеет только подставлять ключ как есть. Это наш вывод, а не цитата.
- Даже будь прокси доступен, подпись пришлось бы считать нам, а для этого нужен секрет.

**Ещё вариант — достать ключи пользователя.**

- `GET /v1/connect/{project}/accounts?include_credentials=true` возвращает учётные данные: https://pipedream.com/docs/connect/api-reference/list-accounts
- Ограничение «нужен свой OAuth-клиент» в документации касается только OAuth-приложений. Биржи подключаются по ключам, поэтому ограничение к ним не относится.
- Значит, ASCN может забирать ключ и секрет и подписывать ордера на своём сервере. Это работает, но ключи пользователей покидают Pipedream, и за их хранение отвечаем мы. Документация прямо предупреждает: «Never return user credentials to the client».

## 3. PR в публичные компоненты

- Технически это возможно: репозиторий открыт, внешние PR принимаются (например, #22167).
- Прецедентов брокерских ID нет:
  - поиск «broker» по репо находит только idx_broker и easybroker (это недвижимость);
  - компонентов binance и okx нет совсем (404);
  - в `bybit.app.mjs` заголовки жёстко зашиты, брокерского параметра тоже нет.
- Минусы PR:
  - сроки ревью непредсказуемы;
  - наш ID нельзя «вшить» в общий компонент, а необязательный проп `headers` или `brokerId` агент должен не забывать передавать в каждом вызове;
  - у Bitget сначала нужно поменять порядок слияния заголовков в `makeRequest`;
  - у MEXC писать нечего — действий нет.
- Это возможный долгосрочный бонус, но не основной путь.

## 4. Своё приложение или приватные компоненты

- **Своё «приложение»** (новый тип авторизации) в Pipedream создают только сами Pipedream: оно попадает в общий реестр через запрос на интеграцию. Нам это не нужно, потому что приложения bingx, bitget и mexc уже есть.
- **Приватные действия поверх существующих приложений** разрешены и работают в Connect для конечных пользователей. Это и есть custom tools из пункта 2.
  - Внутри действия можно импортировать готовый `bingx.app.mjs` или `bitget.app.mjs`, взять их методы подписи и добавить свой заголовок.
  - Либо подписывать запрос самим через `crypto` и `axios`.

## 5. Рекомендация

**Самый простой рабочий путь — свои действия (custom tools) в нашем Pipedream-workspace.**

1. Подключить Business-план Pipedream, если его ещё нет. Без него публиковать нельзя.
2. Написать 3 набора действий с ключами `ascn_*`:
   - **BingX**: `place-order`, `cancel-order`, `get-balance` и generic-вызов.
     - Пропы: `bingx: { type: "app", app: "bingx" }` и параметры ордера.
     - Вызов: `this.bingx.makeRequest({ path, method, params, headers: { "X-SOURCE-KEY": BROKER_ID }, $ })`. Метод уже принимает `headers`.
   - **Bitget**: свой запрос через axios.
     - Заголовки: `{ ...this.bitget.getHeaders({ path, method, params, data }), "X-CHANNEL-API-CODE": CODE }`.
     - Подпись строится той же функцией `preHash`, поэтому её не трогаем.
   - **MEXC**: подпись пишем с нуля. HMAC-SHA256 по query-строке, заголовок `X-MEXC-APIKEY`, плюс `source: BROKER_ID`.
     - Имена полей `$auth` сначала проверить: вывести `Object.keys(this.mexc.$auth)`, как это делает заготовка.
3. Брокерский ID хранить внутри кода действия, а не в пропе. Тогда агент не сможет его пропустить.
4. Опубликовать: `pd publish ... --connect-environment development`, затем `production`.
5. В инструменте `apps` у ASCN запускать `~/ascn_*` вместо публичных `bingx-trade-new-order` и аналогов. Публичные торговые действия для этих бирж скрыть от агентов.
6. Проверить на тестовом ордере, что биржа засчитывает атрибуцию: в кабинете брокера должен появиться оборот от пользователя.

Подключение пользователя не меняется: та же Connect Link с вводом ключа и секрета.

**Запасной вариант** — `include_credentials=true` и подпись на бэкенде ASCN. Этот путь не зависит от компонентов Pipedream, но добавляет ответственность за хранение секретов. Проверить, не ограничен ли он тарифом.

**Что невозможно**

- Добавить заголовок через готовые действия или BingX Generic API Call: нет такого параметра, а у Bitget заголовки перезаписываются.
- Воспользоваться API Proxy для этих бирж: он не включён и не умеет подписывать запросы.
- Торговать на MEXC готовыми действиями: их нет.
- Публиковать custom tools на плане ниже Business.
